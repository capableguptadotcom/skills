# pstack principles: individual critique for a daily skill pack

This is a design judgment about which reasoning habits belong inside **shape, develop, debug, review, research, simplify, handoff, and simulate-discussion**. It is not an installation plan, a source catalog, or a request to synchronize with pstack. My provisional result is to create **no new entrypoint** for any of these 24 leaves. Several have excellent material for an existing owner; others are reminders, overlapping slogans, or rules that need narrower conditions before adoption.

## 1. Attack the Premise

[Current body](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/principle-attack-the-premise/SKILL.md). The useful mechanism is a forced change of experimental question: after repeated failed interventions, state the assumption shared by those interventions and seek an observation that discriminates it from an alternative. This is more actionable than a general instruction to think harder. Its natural home is **debug**, with a smaller version in **research** when several searches are built around the same unproved interpretation. **simulate-discussion** may expose a premise but cannot replace the observation.

It works for TypeScript, Python, infrastructure, and non-code investigations; it needs observational access rather than any library. The two-fix threshold is a useful interruption trigger, not a statistical inference. Two bad implementations do not establish that the premise is false. Likewise, compensating for a condition can be an appropriate controlled mitigation even when removing it is impossible or outside scope. Do not turn the final instruction to remove the condition into permission for a redesign.

**Simulated practitioner:** “Give me one line stating what all failed fixes assumed, then one check that could prove it wrong.” **Strong skeptic:** “The text says each failure is evidence against the premise, but failure may simply show the intervention never reached the relevant path.” **Falsifiable evaluation:** provide a restart failure after two timeout adjustments, with an accessible stale-state cause. Pass if the agent tests whether the failing request executes before another timeout edit; fail if it merely renames the third intervention. Include a control where the premise is true and the earlier patches were ineffective.

**History and disposition:** introduced publicly in [#329](https://github.com/cursor/plugins/commit/e8d856f0273b42ebafe0ec3546bd645709e7c1b0) with a specific per-actor imbalance census. [#633](https://github.com/cursor/plugins/commit/e5136d82418d2db3165ea1050d17577cd618cc05) removes that overfit mechanism and replaces it with a discriminating observation. The conceptual correction is visible; the companion history note describes the PR-reported comparison; this pass did not replicate it. **Keep as a principle inside debug**, preserving the possibility that the premise survives the test.

## 2. Boundary Discipline

[Current body](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/principle-boundary-discipline/SKILL.md). This proposes two separations: translate untrusted external representations into domain values once, and keep framework wiring thin enough that business decisions can run without the framework. The best part is its additional requirement that public interfaces expose domain concepts rather than storage or transport details. **shape** owns choosing these seams; **develop** implements them; **review** checks for representation leakage. It overlaps with model-the-domain and type-system-discipline and should not become a fourth architecture workflow.

The absolute “trust internal code unconditionally” is too strong. TypeScript types disappear at runtime, mutable objects can violate earlier checks, and Python annotations alone do not enforce validation. An invariant may need checking at a mutation or ownership boundary even inside one service. Pure logic is valuable when it separates actual decisions from effects; extracting every small calculation into a function adds reader work. No host integration is required, but the language's type and mutation guarantees must be understood.

**Simulated practitioner:** “Parse the config once; let the core accept the parsed configuration.” **Strong skeptic:** “Calling an unchecked Python dict internal does not make its values trustworthy.” **Falsifiable evaluation:** supply a CLI with repeated config validation and a second internal mutation that can invalidate the config. Pass if the agent consolidates raw-input parsing but preserves or structurally removes the mutation hazard; fail if it deletes checks just because they are below the entrypoint.

**History and disposition:** present at [initial public import](https://github.com/cursor/plugins/commit/24bd6eb895d63a6e76fabfea2cb344384d177d79). [#175](https://github.com/cursor/plugins/commit/45c66fde1f1681a902a30d1ae8bca1cc64465d6e) explicitly changes “parse lazily at use-site” to parse at the boundary and adds domain-facing interfaces. Later prose changes do not establish correctness. No per-skill trial data was found. **Adapt within shape/develop**: trust established invariants, not an internal-directory label.

## 3. Build the Lever

[Current body](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/principle-build-the-lever/SKILL.md). The core contribution is a reproducible transformation or verification artifact: learn one unit manually, automate the recipe, compare the automated result with that unit, and ensure reruns are safe. For a migration, this makes **develop** and **simplify** more reviewable. For **research**, a small extraction or consistency check can substantiate a result. **handoff** benefits from the rerun command and its evidence. The rule that a deterministic pass should beat manual delegate fan-out is especially useful.

The current text overreaches by requiring a file for virtually all nontrivial work and saying a tool reruns “for free.” Tool creation, review, maintenance, and erroneous repeated edits all cost something. Existing test commands and a well-specified manual check may already provide sufficient repeatability. TS codemods and Python scripts are possible implementations, not dependencies. Shell/runtime availability and filesystem permissions vary; a portable owner must use available tooling and must not require a delegate skill outside its installation.

**Simulated practitioner:** “A reviewer should rerun the transform rather than repeat my hundred edits.” **Strong skeptic:** “For four subtle changes, a new script may be harder to verify than the changes.” **Falsifiable evaluation:** compare a 60-call-site mechanical migration with a three-line semantic bug. Pass if the migration gets a bounded, rerunnable transform with a checked sample and the small fix avoids unnecessary tooling; fail if the same mandatory artifact rule governs both.

**History and disposition:** [#84](https://github.com/cursor/plugins/commit/7b1c32e4c3427c30ad2595630ed74815c52fe4e9) begins with repetitive work and explicit amortization; [#91](https://github.com/cursor/plugins/commit/65f4dacee2ed677a295de8d295b889bbfe2ad27c) adds delegate recipes; [#102](https://github.com/cursor/plugins/commit/ba7781cce69f65bf3edc0e789d28233d9e967f96) deliberately broadens it to nontrivial one-offs and requires a file. [#538](https://github.com/cursor/plugins/commit/00b14f1df36b32a8dd1529324a3a459f6563b127) mainly compresses prose. This is visible policy expansion, not proof of payoff. **Adapt**, retaining the original cost-sensitive condition.

## 4. Encode Lessons in Structure

[Current body](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/principle-encode-lessons-in-structure/SKILL.md). The description carries most of this leaf: when a correction recurs, see whether a lint, schema, runtime check, or metadata constraint can remove the need to remember it. The surviving body says judgment-dependent lessons need clearer instructions and an example, and structural fixes should replace textual reminders. This belongs to **develop** when a concrete failure is observed and **simplify** when duplicated rules are being consolidated. It overlaps with tests, type design, and build-the-lever; it does not warrant a session-learning system.

Repeated wording is only a clue. Some repetition reflects different contexts, and automated enforcement can lock in an unsettled preference. Removing all explanatory text after installing a lint also loses rationale and remediation guidance. In TS the enforcement might be a type or lint; in Python it might be a schema, test, or runtime boundary check. None requires persistent conversation capture, a private “brain,” or cross-session logging.

**Simulated practitioner:** “The third missed import rule should fail mechanically instead of becoming a louder reminder.” **Strong skeptic:** “A linter can repeatedly enforce the wrong rule; recurrence alone is not a specification.” **Falsifiable evaluation:** give one repeated forbidden-import correction and one disputed naming preference. Pass if only the settled import invariant gets enforcement, with a failing example and a valid counterexample; fail if the naming preference becomes a broad rule or if conversation logs are collected.

**History and disposition:** the [initial import](https://github.com/cursor/plugins/commit/24bd6eb895d63a6e76fabfea2cb344384d177d79) already contains the concept; [#114](https://github.com/cursor/plugins/commit/64fe0147d32e0c05d2953501ddf9ff65ebcadc54) adds an enforcement-strength ladder. [#571](https://github.com/cursor/plugins/commit/08bd59b37834550f5e8fa0bb5e8852204a7534cf) cuts that ladder and the capture/routing loop, leaving two sentences. The cut's behavioral-equivalence claim is not backed by visible runs. **Keep as a short principle**, with explicit settled-rule and cost conditions; do not restore personal learning machinery.

## 5. Exhaust the Design Space

[Current body](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/principle-exhaust-the-design-space/SKILL.md). The operative instruction is now almost entirely in frontmatter: for a genuinely novel UI or architecture choice, make two or three competing prototypes and compare them. The body only adds feel-dependent product choices. The valuable mechanism is externalizing alternatives so a team can inspect consequences; the title's promise to “exhaust” a space is unrealistic. **shape** should own this as optional exploration; **simulate-discussion** can challenge the criteria, while a runnable sketch answers questions rhetoric cannot.

Neither TS nor Python is assumed. A prototype may be HTML, a minimal Python experiment, a state diagram, or an interface example. The host must support whatever artifact is appropriate, with no mandatory parallel agents or image generator. Where a precedent already fits, a defect is localized, or constraints admit one viable approach, more variants waste time. Two near-identical layouts do not test two approaches; two dramatic alternatives that ignore constraints do not help either.

**Simulated practitioner:** “Seeing two genuinely different interaction loops reveals a choice that prose hid.” **Strong skeptic:** “A quota of three sketches can produce theater rather than uncertainty reduction.” **Falsifiable evaluation:** give a novel bulk-selection interaction and an ordinary established settings field. Pass if the first explores distinct interaction models with explicit comparison criteria and the second follows precedent; fail if both receive a fixed design tournament.

**History and disposition:** present in the [initial import](https://github.com/cursor/plugins/commit/24bd6eb895d63a6e76fabfea2cb344384d177d79), touched by [#175](https://github.com/cursor/plugins/commit/45c66fde1f1681a902a30d1ae8bca1cc64465d6e), and reduced to its current near-stub by [#571](https://github.com/cursor/plugins/commit/08bd59b37834550f5e8fa0bb5e8852204a7534cf), which deletes the useful non-applicability cases. Public evidence does not show that all hosts infer those boundaries. **Adapt as a shape reference**, preserving conditional use and genuinely distinct alternatives.

## 6. Experience First

[Current body](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/principle-experience-first/SKILL.md). This establishes the target for design: improve the central workflow, justify controls, reduce feature count when necessary, and consider the consumer and future maintainer. Its practical mechanism is a scope test—what does this feature do for the core loop?—plus attention to feedback and error states. **shape** owns that tradeoff; **review** can check promised user behavior; **handoff** should explain impact through the consumer's task. It overlaps with subtract-before-you-add but supplies a user-facing reason for subtraction.

“Delight over convenience” is not a sufficient decision rule when accessibility, correctness, operating cost, or an explicit deadline is at issue. A maintainer's experience and an end user's experience can conflict; the document says to weigh both without resolving the conflict. This is language- and host-neutral, and applies to TS UIs and Python libraries alike. Prototyping should resolve material uncertainty, not become mandatory before every small feature.

**Simulated practitioner:** “A clear failure message can matter more than a fourth feature.” **Strong skeptic:** “An agent may label its own visual taste ‘delight’ and spend the budget polishing the wrong thing.” **Falsifiable evaluation:** offer a constrained feature request with an unfinished core error path and several optional controls. Pass if the proposal traces priority to the user's stated workflow and access needs; fail if visual polish or invented features displace required behavior.

**History and disposition:** [#103](https://github.com/cursor/plugins/commit/c532aa167cdbceb3440706ceacea2361e4d395df) expands the original UI-oriented principle to library consumers and maintainers. Later [#329](https://github.com/cursor/plugins/commit/e8d856f0273b42ebafe0ec3546bd645709e7c1b0) and [#331](https://github.com/cursor/plugins/commit/d7cde2b84eadbcd6fd890302c876f4436ccb6d82) are density/prose passes, not user-outcome studies. Feedback remains sparse. **Keep as a principle in shape**, phrased as observable workflow quality rather than unmeasured delight.

## 7. Explain the Number

[Current body](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/principle-explain-the-number/SKILL.md). This is unusually strong material: decide what evidence would change the decision before running; inspect the limiter; rule out skipped work, errors, unequal tuning, and noise; retain run count and spread with the claim. **research** should own experimental comparison, **debug** should own performance diagnosis, and **review/handoff** should distinguish evidence from a headline number. It complements prove-it-works: producing an output and measuring the intended work are different claims.

The [benchmark dependency](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/benchmark-checklist/SKILL.md) is worth retaining as adapted reference material. It has a one-run ballpark exception, alternating repeated runs, end-to-end relevance, and explicit correctness/work checks. Its Linux commands (`uptime`, `nproc`, `pidstat`, `perf`, `strace`) need host equivalents on Windows; Node/Python profiler availability varies. “Why not double?” is useful for throughput but does not literally identify a resource limiter for every accuracy eval. Spread greater than effect means the comparison is unresolved under this design, not that a different or larger experiment can never resolve it.

**Simulated practitioner:** “The 40% speedup disappears when we count successful requests.” **Strong skeptic:** “A universal limiter demand can make an honest descriptive measurement impossible to report.” **Falsifiable evaluation:** supply A/B benchmark output where B skips half the work, plus a legitimate noisy comparison. Pass if the agent rejects the first claim and labels the second inconclusive with its uncertainty; fail if it reports the fastest median or fabricates a bottleneck.

**History and disposition:** publicly added in [0.15.6 port](https://github.com/cursor/plugins/commit/23e4138daa01c42d4969f7a5465f82704e64f798), compressed in [#538](https://github.com/cursor/plugins/commit/00b14f1df36b32a8dd1529324a3a459f6563b127), strengthened in [#986](https://github.com/cursor/plugins/commit/ab1f702ce8e8b6557edb56b09f52cde8bfb83f17) with a pre-run decision/noise statement. No per-principle comparative trials are supplied. **Adapt with high priority inside research**, retaining honest descriptive and ballpark exceptions.

## 8. Fix Root Causes

[Current body](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/principle-fix-root-causes/SKILL.md). The important reasoning step is to distinguish a legitimate state that was mishandled from an impossible state produced earlier. A guard is correct in the former and may conceal the latter. Reproduction, instrumentation, causal tracing, and checking other instances form a coherent **debug** procedure; an inexpensive diagnostic signal is a useful follow-through. Attack-the-premise is a recovery step inside this procedure, not a competing workflow.

Both TS and Python benefit, with no particular framework or host. “Fix every instance” still needs a bounded shared mechanism and scope; a localized bug does not authorize an unrelated sweep. Persisted state is a useful restart hypothesis, not a reason to delete caches before preserving evidence. The claim that a paragraph-long workaround comment proves the code wrong is unsound: compatibility constraints and external faults can justify documented workarounds. Fixing an upstream cause may be outside the available system.

**Simulated practitioner:** “An absent record is legal here, so handling absence is the fix rather than a cover-up.” **Strong skeptic:** “Root-cause language can delay a necessary mitigation or turn a small patch into an architecture crusade.” **Falsifiable evaluation:** pair a legal cache miss with an illegally dropped record. Pass if the agent handles the miss at the consumer and traces the dropped record to its producer, preserving a regression check for each; fail if it bans guards or swallows both symptoms.

**History and disposition:** [#604](https://github.com/cursor/plugins/commit/36cecbf2b5089b275254d59cb4612d6f96f00fbd) adds a cheap always-on signal after a difficult diagnosis. [#633](https://github.com/cursor/plugins/commit/e5136d82418d2db3165ea1050d17577cd618cc05) explicitly corrects the former “do not add guards” rule by explaining legitimate state. The visible evolution is substantive; the author-reported #633 trial and its limits are described in the companion history note, not independently replicated here. **Keep as a debug principle**, omitting the comment-length heuristic and bounding scope.

## 9. Foundational Thinking

[Current body](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/principle-foundational-thinking/SKILL.md). This bundles several habits: choose data shapes for access patterns, share structure rather than superficially similar statements, isolate concurrent mutation, and install infrastructure that enables subsequent work. Its best contribution is asking which early decision makes later work simpler. **shape** owns the data/ownership choices and **develop** owns necessary scaffold sequencing. Model-the-domain, separate-before-serializing, and sequence-verifiable-units are sharper expressions of most of its content.

The scaffold-first wording can be misread as permission to add CI, lint, shared types, and test infrastructure to any feature request. The correct question is which missing foundation this task actually needs. Likewise, removing dead code before scaffolding conflicts with surgical changes when the code is unrelated. TS types and Python domain models can both support the data-first method; Python's runtime guarantees must not be confused with TS compile-time checking. No agent machinery is necessary.

**Simulated practitioner:** “Choosing ownership before writing concurrent workers saves coordination logic later.” **Strong skeptic:** “Every speculative framework can be sold as something future phases will benefit from.” **Falsifiable evaluation:** provide a small repository with adequate existing infrastructure and a new query feature. Pass if the agent names the needed data shape and uses existing checks; fail if it first creates a generic scaffold or deletes adjacent dead code.

**History and disposition:** present at the [initial import](https://github.com/cursor/plugins/commit/24bd6eb895d63a6e76fabfea2cb344384d177d79); [#175](https://github.com/cursor/plugins/commit/45c66fde1f1681a902a30d1ae8bca1cc64465d6e) adds coherent abstraction/deepening rather than special-case coordination across callers. Subsequent changes are prose-focused. There is no separate demonstrated feedback loop here. **Reference rather than preserve as another named principle**: distribute its useful questions to the existing shape/develop sections.

## 10. Guard the Context Window

[Current body](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/principle-guard-the-context-window/SKILL.md). The description advocates routing bulk to delegates; the remaining body advocates sizing phases, limiting files, and accounting for mechanism costs. The real mechanism is evidence compression: retain the question, findings, citations, and unresolved risks while avoiding repeated raw payloads. **research** needs bounded reading and source pointers; **handoff** needs reliable state transfer; **develop/review** should narrow search and output. This is an execution habit shared by owners, not a user activity.

Neither TS nor Python is implicated. Host context limits and delegation policies are central. A small pack must remain useful when no delegates are available or authorized. Delegation does not make evidence free: a summary can omit the decisive caveat, and parallel reading can duplicate effort. Prefer targeted searches and bounded output first; use delegation where it actually partitions work. Preserve direct source access for claims that matter.

**Simulated practitioner:** “Give the main thread the three findings and exact paths, not a thousand-line dump.” **Strong skeptic:** “A summary can conceal the contradiction the lead needed to see.” **Falsifiable evaluation:** give a large log containing an early ordinary failure and a late causal exception. Pass if bounded extraction preserves both the finding and the exception with locations; fail if summarization drops the exception or agent fan-out becomes mandatory.

**History and disposition:** [#419](https://github.com/cursor/plugins/commit/b0b9c7a0baf8b6aa1d00bf77d4101e577d4ba411) is a model-specific instruction cut; [#571](https://github.com/cursor/plugins/commit/08bd59b37834550f5e8fa0bb5e8852204a7534cf) deletes payload isolation and the rule about keeping common content inline. The current description still supplies a delegation instruction missing from the body. No portable evaluation establishes these cuts. **Adapt as shared execution guidance**, with evidence-preserving summaries and optional delegation.

## 11. Laziness Protocol

[Current body](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/principle-laziness-protocol/SKILL.md). The surviving mechanism is only two rules: centralize a repeated decision and minimize the change. Those are valuable in **simplify** and **develop**, with **review** checking for needless indirection. It overlaps heavily with subtract-before-you-add and minimize-reader-load; keeping all three as independent triggers creates more vocabulary than distinct behavior.

“Pass the result as a simple flag” is not universally simpler: a boolean can erase meaning, and an existing domain value may be the better source of truth. Fewer lines can also compress code into something harder to read. TS and Python need the same semantic judgment; no host dependency exists. Keep the smallest behavioral change, not the smallest textual diff at any cost. A broad rewrite is still inappropriate when a local fix solves the task.

**Simulated practitioner:** “We already decide this once; consumers should use that result.” **Strong skeptic:** “A one-line expression with hidden state can be worse than a clear five-line branch.” **Falsifiable evaluation:** offer duplicated policy decisions alongside two superficially similar but independent branches. Pass if the common policy gains one clear owner and the independent branches remain explicit; fail if all repetition becomes a helper or an opaque boolean spreads through the call chain.

**History and disposition:** [#175](https://github.com/cursor/plugins/commit/45c66fde1f1681a902a30d1ae8bca1cc64465d6e) distinguishes deep interfaces from deep call chains. [#571](https://github.com/cursor/plugins/commit/08bd59b37834550f5e8fa0bb5e8852204a7534cf) removes deletion, flattening, signal-threading, leak, and fatigue advice, leaving the current pair. That is consolidation by subtraction, not visible proof of improved decisions. **Keep the two ideas within simplify**, without a separate “protocol” identity or unconditional flag prescription.

## 12. Make Operations Idempotent

[Current body](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/principle-make-operations-idempotent/SKILL.md). This is a concrete lifecycle design question: derive the next action from actual state, reconcile partial progress, and ensure a repeat converges. It asks what happens after a crash at each mutation point, including abandoned markers and claimed work. **shape** should expose this requirement for commands and workers; **develop** implements reconciliation; **review** checks crash paths. It complements separation of shared state but addresses interrupted execution rather than concurrent ownership.

This transfers well to TS jobs and Python CLIs, but filesystem rename atomicity, lock identity, process detection, and external idempotency support are host-dependent. Convergence of final local state is not enough when a repeated run sends two payments or messages. Some operations cannot be made idempotent without external keys, transactions, or durable records. The owner must identify those limits and authorization boundaries rather than promise universal repeat safety.

**Simulated practitioner:** “The second run should finish the first run's work instead of asking me to clean a lock.” **Strong skeptic:** “A correct final record can hide a duplicated external effect.” **Falsifiable evaluation:** interrupt a synthetic import at each persistence boundary and rerun it, including immediately before and after an external-effect acknowledgement. Pass if records converge and effects occur exactly as the contract permits; fail if a retry duplicates the effect or stale detection guesses from age alone.

**History and disposition:** present in [initial import](https://github.com/cursor/plugins/commit/24bd6eb895d63a6e76fabfea2cb344384d177d79). [#633](https://github.com/cursor/plugins/commit/e5136d82418d2db3165ea1050d17577cd618cc05) replaces a fixed list including PID-based lock detection with state-derived reconciliation and evidence valid at every crash point. This is a useful move away from host-specific prescriptions. The companion history note records the author-reported lock comparison in #633; this pass did not rerun it. **Keep as a conditional shape/develop principle**, explicitly including observable external effects.

## 13. Migrate Callers Then Delete Legacy APIs

[Current body](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/principle-migrate-callers-then-delete-legacy-apis/SKILL.md). The description proposes one coordinated internal migration instead of retaining two APIs. The remaining body says to update contract tests and lists applicability: no external compatibility dependents, ability to absorb a break, and a simplification initiative. The mechanism is bounded ownership: inventory consumers, move them to one contract, and remove the obsolete path. **simplify** owns this workflow, with **develop** executing and **review** verifying that the inventory and compatibility claim hold.

TS static references help but miss dynamic imports and configuration; Python monkeypatching, plugins, reflection, and entrypoints make a search-only inventory especially incomplete. Host tooling matters less than actual release boundaries. “Internal” is a deployment relationship, not a folder name. Independently deployed services or a published package can need compatibility even in a private repository. Deleting tests merely because they mention the old API is unsafe if they also encode promised behavior.

**Simulated practitioner:** “There are six callers under one release; migrate all six and remove the adapter.” **Strong skeptic:** “The seventh caller may be a plugin loaded by name, so the clean diff hides a breaking release.” **Falsifiable evaluation:** supply a statically visible caller set and one documented dynamic consumer. Pass if the agent inventories both and keeps or plans compatibility where release boundaries require it; fail if a zero-result symbol search justifies deletion.

**History and disposition:** from [initial import](https://github.com/cursor/plugins/commit/24bd6eb895d63a6e76fabfea2cb344384d177d79), density-edited in [#329](https://github.com/cursor/plugins/commit/e8d856f0273b42ebafe0ec3546bd645709e7c1b0), then heavily cut in [#634](https://github.com/cursor/plugins/commit/99743e9c151c8537cbbf1f98bb38f34ef3368453). That cut removes explicit caller inventory, immediate deletion, and exceptional/time-boxed adapters, relying on the title/description. No visible runs show that this reduced body preserves the inventory step. **Adapt as a simplify migration reference**, restoring the consumer evidence rather than a deletion slogan.

## 14. Minimize Reader Load

[Current body](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/principle-minimize-reader-load/SKILL.md). This gives **simplify** a better target than line count: reduce the indirections a reader must chase and the mutable state they must remember. Those axes can move independently. The interface-compression test—does this boundary hide meaningful decisions?—also gives **shape** and **review** a specific way to discuss abstractions. Naming an invariant once and deriving state instead of synchronizing it are useful mechanisms.

The examples risk making one caller or one implementation sufficient grounds to inline. A single-use seam can hide a complicated dependency, ownership rule, or security boundary. The 30-second question is a heuristic, sensitive to prior familiarity and task complexity. TS and Python have no fundamental difference here; dynamic dispatch and runtime-generated values can make tracing harder in either. No host or specialized complexity tool is required, and a small pack should not turn this into a numeric scoring bureaucracy.

**Simulated practitioner:** “I can answer who changes this value without opening six wrappers.” **Strong skeptic:** “Flattening a meaningful module makes the first read easier and every later change riskier.” **Falsifiable evaluation:** give a pass-through adapter chain and a single-caller module hiding protocol complexity. ## 15. Model the Domain

[Current body](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/principle-model-the-domain/SKILL.md). This is one of the strongest architecture leaves. Instead of accumulating synchronized booleans and repeated conditions, select a state machine, tagged model, table, reducer, index, or ownership boundary matching the actual invariants and access patterns. It explicitly resists an abstraction that adds indirection without removing a real cost. **shape** is the owner; **develop** applies it locally; **simplify** can recover a scattered model. It supplies the concrete data-centered content that foundational-thinking only gestures toward.

TS discriminated unions make some invalid combinations rejectable by a checker; Python dataclasses, enums, tagged unions, and constructors can express the same model, with runtime validation where needed. A table is not automatically superior to a short if-chain, and adding a new branch is a signal to inspect, not proof the design is wrong. Organizing by domain knowledge can coexist with a readable pipeline; sequence-named modules are not inherently defective. No host-specific integration is needed.

**Simulated practitioner:** “One lifecycle value replaces two booleans that must stay synchronized.” **Strong skeptic:** “A registry can obscure straightforward control flow and make a three-case function harder to navigate.” **Falsifiable evaluation:** present an invalid-state bug caused by boolean combinations plus a clear local three-case calculation. Pass if the former gains a coherent model and the latter stays simple; fail if both receive a framework or the new model still constructs the forbidden state.

**History and disposition:** introduced by [#147](https://github.com/cursor/plugins/commit/a8145426e541afa424a403e3866496216c1b8142); [#175](https://github.com/cursor/plugins/commit/45c66fde1f1681a902a30d1ae8bca1cc64465d6e) adds organization around domain knowledge; [#538](https://github.com/cursor/plugins/commit/00b14f1df36b32a8dd1529324a3a459f6563b127) condenses wording. No per-skill outcome data is visible. **Keep as a shape principle**, including its valuable do-not-force condition.

## 16. Never Block on the Human

[Current body](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/principle-never-block-on-the-human/SKILL.md). This addresses needless permission turns: infer reasonable execution details, complete reversible work, and present a concrete result for asynchronous review. It also says product direction comes from the human and names irreversible actions as confirmation cases. All execution owners need this habit, especially **develop** and **handoff**. It does not create a standalone deliverable or procedure worth another skill.

Reversibility alone does not establish scope or authorization: rewriting unrelated notes, splitting tasks, or changing a product default can still be wrong. Conversely, an external action already authorized by the user does not need repeated approval merely because it is consequential. The current user's and host's instruction hierarchy must own those decisions. This is language-neutral; the host's available tools and permission model are the material assumptions. The leaf's suggestion to fix a discovered problem in the next round must not create an unsolicited backlog or background loop.

**Simulated practitioner:** “Finish the authorized patch and show the diff instead of asking if I should open the file.” **Strong skeptic:** “An agent can call a product decision reversible and quietly take ownership it was never given.” **Falsifiable evaluation:** combine a clear local bug, an ambiguous product behavior, and an external message request absent from the user's scope. Pass if the bug progresses autonomously while the latter actions respect direction and authorization; fail if every action is blocked or all three are performed under a reversibility slogan.

**History and disposition:** present at [initial import](https://github.com/cursor/plugins/commit/24bd6eb895d63a6e76fabfea2cb344384d177d79); [#419](https://github.com/cursor/plugins/commit/b0b9c7a0baf8b6aa1d00bf77d4101e577d4ba411) removes the explicit “genuine ambiguity” exception; [#538](https://github.com/cursor/plugins/commit/00b14f1df36b32a8dd1529324a3a459f6563b127) removes formatting headings. No autonomy outcome evidence is supplied. **Adapt into shared execution wording**, preserving settled authorization and genuine ambiguity; reject the absolute title as an operating rule.

## 17. Outcome-Oriented Execution

[Current body](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/principle-outcome-oriented-execution/SKILL.md). This permits planned temporary breakage within a bounded rewrite so the agent does not create throwaway compatibility layers solely to keep every intermediate edit green. It retains local checks and full static/runtime verification at completion. **develop** and **simplify** own this exception; **shape** should state where breakage is allowed. It overlaps with migrate-callers and apparently conflicts with sequence-verifiable-units unless “unit” means a coherent verification boundary rather than every edit.

For TS, temporary compile failures may be tolerable on an isolated change; for Python, passing imports can still conceal runtime breakage. Neither language makes intermediate broken commits safe for users or collaborators. Shared branches, production deploys, and independently released consumers require stronger continuity. No specific host is needed, but isolated working state and an explicit scope are material preconditions. “End state” should not excuse delaying all checks until the end.

**Simulated practitioner:** “We can change the internal signature and its callers together without building a disposable adapter.” **Strong skeptic:** “An agent can spend hours on a broken branch and call its missing feedback a planned phase.” **Falsifiable evaluation:** give a coordinated internal rename and a live service migration. Sparse change history is neither validation nor a defect. **Reference as a narrow migration exception**, with an explicit relationship to verifiable units, not an always-on principle.

## 18. Prove It Works

[Current body](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/principle-prove-it-works/SKILL.md). This asks for observation of the actual promised artifact or behavior instead of a compiler result, timestamp, cached view, or delegate summary. A repeatable check is preferred where practical. **develop/debug** own direct exercise, **review** inspects the diff and behavior evidence, **research** checks cited sources, and **handoff** reports what was observed and what remains unknown. Its generic breadth is useful as a completion rule, not another entrypoint.

“Suspect the observation method before the system” should mean validate the instrument, not dismiss failing evidence. Direct observation also does not make a single sample general proof. TS type checking and Python import success are necessary in some contexts but do not demonstrate a feature path. The [show-me-your-work dependency](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/show-me-your-work/SKILL.md) brings a TSV helper, Cursor transcript audit paths, and cross-model review requirements; those do not belong in a portable completion rule. Evidence can be a native test, screenshot, value readback, or an explicitly limited manual observation.

**Simulated practitioner:** “Read the generated file and run the path the user will use.” **Strong skeptic:** “A one-time happy-path screenshot can be presented as proof of a whole feature.” **Falsifiable evaluation:** provide a build that passes while a UI action writes the wrong destination, plus stale screenshot evidence. Pass if the agent exercises the actual action and checks the persisted value; fail if build success or screenshot freshness closes the task.

**History and disposition:** [#78](https://github.com/cursor/plugins/commit/35f33923cde39e9c27d68d95517e4e4e83719c7c) connects auditable work; [#414](https://github.com/cursor/plugins/commit/70b2dc8b4b85c8d5648624ca40d692c421fff32f) and [#419](https://github.com/cursor/plugins/commit/b0b9c7a0baf8b6aa1d00bf77d4101e577d4ba411) cut explicit run-the-path and delegation examples. No published comparison establishes that every model supplies them unaided. **Keep as a completion principle**, with proportional evidence and explicit runtime limits.

## 19. Redesign From First Principles

[Current body](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/principle-redesign-from-first-principles/SKILL.md). This is a counterfactual design exercise: ask what design would follow if the new requirement had always existed, then propagate the chosen change coherently through types, examples, and rationale while delivering incrementally. **shape** can use the counterfactual to detect a poor patch point. **simplify** may execute a redesign when the user actually asked for one; **develop** should not inherit an automatic rewrite mandate. Unlike attack-the-premise, this questions the design under new constraints rather than an empirical belief.

The categorical instruction to redesign whenever integrating a requirement conflicts with surgical changes. Existing compatibility, migration cost, and settled decisions are requirements too. A greenfield answer can illuminate an improved seam without justifying all of it now. This is independent of TS/Python syntax and of host tools. Reading all affected files and updating references are sound within the chosen scope; reading or changing the entire system is not implied.

**Simulated practitioner:** “If we had known about multi-tenancy, this cache key would have included the tenant.” **Strong skeptic:** “A one-field requirement becomes an excuse to rewrite storage because the agent prefers the imaginary greenfield design.” **Falsifiable evaluation:** provide one requirement that reveals an invalid ownership boundary and another supported by a small local extension. Pass if the first gets a justified seam change and the second remains local; fail if both become full redesigns.

**History and disposition:** present at [initial import](https://github.com/cursor/plugins/commit/24bd6eb895d63a6e76fabfea2cb344384d177d79); [#329](https://github.com/cursor/plugins/commit/e8d856f0273b42ebafe0ec3546bd645709e7c1b0) and [#538](https://github.com/cursor/plugins/commit/00b14f1df36b32a8dd1529324a3a459f6563b127) condense the framing rather than add demonstrated outcomes. No per-skill feedback supports a universal redesign policy. **Reject the unconditional rule; adapt the counterfactual as a shape question** with compatibility and scope in the comparison.

## 20. Separate Before Serializing Shared State

[Current body](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/principle-separate-before-serializing-shared-state/SKILL.md). The mechanism is excellent: distinguish independent facts that accidentally share a write target from a real shared invariant. Give independent writers owned state and merge at a read boundary; serialize genuine shared updates with structural coordination. The example of two workers changing separate keys in one JSON file exposes a common lost-update bug. **shape** owns state ownership, **develop** implements it, and **debug/review** investigate races. Idempotence handles retry/crash semantics separately.

The model applies equally to TS asynchronous workers, Python processes, and multiple agents. Async execution is not immunity from logical races, and the Python GIL is not a cross-process consistency mechanism. Lockfiles, atomic compare-and-swap, and file replacement differ by OS/storage backend. Separation is wrong when two values must change atomically together; a lock is not inherently a smell if it protects a real invariant. Independent files also need a coherent read model where snapshots matter.

**Simulated practitioner:** “Metrics and indexing publish separate facts; they do not need to overwrite the same JSON object.” **Strong skeptic:** “Splitting account balance and its ledger marker destroys the transaction we needed.” **Falsifiable evaluation:** pair independent worker counters with a transfer requiring atomic debit/credit. Pass if the first gets isolated ownership and the second gets transactional coordination; fail if all shared state is split or locks are prescribed before ownership analysis.

**History and disposition:** already present under this name in [initial import](https://github.com/cursor/plugins/commit/24bd6eb895d63a6e76fabfea2cb344384d177d79); [#329](https://github.com/cursor/plugins/commit/e8d856f0273b42ebafe0ec3546bd645709e7c1b0) trims wording, and [#331](https://github.com/cursor/plugins/commit/d7cde2b84eadbcd6fd890302c876f4436ccb6d82) adjusts punctuation. No earlier public renamed “serialize” principle was found, and no concurrency trial accompanies this leaf. **Keep as a conditional shape principle**, explicitly preserving joint invariants.

## 21. Sequence Verifiable Units

[Current body](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/principle-sequence-verifiable-units/SKILL.md). This connects execution order and review order: make a coherent change, observe its result before building on it, and arrange delivery so a reviewer can reconstruct the argument. A failing regression followed by a fix is one form; baseline then treatment or removal then reshape are others. **develop/debug/simplify** own the checkpoints; **handoff** owns the concise proof trail. It complements real-artifact verification rather than replacing it.

The text's insistence on every change being green sits awkwardly beside its canonical failing-test commit and outcome-oriented-execution's allowed intermediate breakage. Resolve this by defining meaningful boundaries and intentional red evidence, not pretending the rules are already consistent. Rebase onto clean trunk is also not universally authorized or appropriate: inspect baseline first, preserve existing work, and use the project's branch policy. TS typechecks and Python test subsets can provide cheap targeted feedback, but not every edit needs the entire suite or a separate commit.

**Simulated practitioner:** “Find the first unit that changed the result rather than debug a 90-file batch.” **Strong skeptic:** “Per-line testing and mandatory rebasing can cost more than they localize, and can disturb the user's work.” **Falsifiable evaluation:** supply a multi-file migration with cheap local checks and an expensive full suite. **History and disposition:** [#123](https://github.com/cursor/plugins/commit/27daaa309189aabce2dcaa2554cc940d65749a25) introduces both execution and delivery sequencing; [#414](https://github.com/cursor/plugins/commit/70b2dc8b4b85c8d5648624ca40d692c421fff32f) removes a repeated pattern block. ## 22. Subtract Before You Add

[Current body](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/principle-subtract-before-you-add/SKILL.md). This is an ordering heuristic: remove obsolete complexity in the affected path before layering new behavior onto it. It also argues against speculative validation and redundant prompt text. **simplify** is the obvious owner; **shape** can ask whether the requested capability is already achievable by removing an obstacle. Most remaining content overlaps with laziness-protocol and minimize-reader-load; the distinct contribution is ordering removal before replacement.

Deletion is not automatically safer than addition. Deadness requires evidence, old compatibility paths can still serve users, and validators may enforce an actual trust boundary even if the current example is valid. TS compiler reachability and Python test coverage cannot prove no external consumers exist. The host is otherwise irrelevant. The daily pack's surgical rule should win: do not remove unrelated dead code merely to “lay a simpler foundation.” Prompt stubs may carry discoverability even when they contain little prose.

**Simulated practitioner:** “Delete the unused intermediate representation before adding a second conversion.” **Strong skeptic:** “The instruction turns a feature patch into a cleanup sweep and calls the larger diff simplicity.” **Falsifiable evaluation:** provide obsolete code in the exact path being replaced and unrelated dead code elsewhere. Pass if only the former is removed after checking consumers; fail if the agent performs a repository-wide purge or removes a real boundary guard.

## 23. Test Behavior, Not Implementation

[Current body](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/principle-test-behavior-not-implementation/SKILL.md). This is the clearest test-quality mechanism in the set: imagine a behavior-breaking edit and an implementation-only edit. A useful test should catch the former and survive the latter. It defines observable effects broadly enough to include an external request payload, readable persisted state, absence of a charge, and invariants. **develop/debug** own writing such tests; **review** uses the two edits to identify hollow or brittle evidence; **simplify** preserves contract coverage through refactors.

The principle is framework-neutral despite its Jest-flavored history. TS compile-time contract tests and Python runtime tests are both legitimate; mocking an external service can test an observable boundary. It should not ban all internal tests: algorithms, performance constraints, and fault injection may need deliberate lower-level checks, with the contract stated. Deleting a brittle test without replacement can silently lose behavior coverage. Mutation checks are a reasoning aid here; running a mutation framework is optional and should be proportional.

**Simulated practitioner:** “This test proves an empty cart never charges and that the spy can see a charge on a nonempty cart.” **Strong skeptic:** “An agent may call a hard-to-exercise test implementation detail and delete the only protection.” **Falsifiable evaluation:** give tests for empty results, forbidden external calls, a private helper call sequence, and a self-derived expected value. Pass if the meaningful absence tests survive, the sequence test is replaced with contract coverage, and the self-reference is corrected; fail if matcher names determine deletion.

**History and disposition:** [#329](https://github.com/cursor/plugins/commit/e8d856f0273b42ebafe0ec3546bd645709e7c1b0) adds a broad matcher/absence blacklist; [#538](https://github.com/cursor/plugins/commit/00b14f1df36b32a8dd1529324a3a459f6563b127) condenses it; [#633](https://github.com/cursor/plugins/commit/e5136d82418d2db3165ea1050d17577cd618cc05) replaces that overreach with the two imagined edits and explicit legitimate absence cases. This correction is visible; the companion history note covers the reported contract-test comparison in #633. No independent replication was performed here. **Keep as a high-priority develop/review principle**, using the current reasoning rather than the earlier blacklist.

## 24. Type System Discipline

[Current body](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/principle-type-system-discipline/SKILL.md). The current body retains semantic brands, parsing raw data into a domain model, and schema-derived types; its description also promises impossible-state modeling and exhaustiveness. **shape/develop** own the modeling, **review** checks mismatched identities and unchecked input. This overlaps heavily with boundary-discipline and model-the-domain. Language-specific syntax belongs in a conditional owner reference, not a separate universally triggered daily skill.

The [TS dependency](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/typescript-best-practices/SKILL.md) and [patterns](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/typescript-best-practices/references/patterns.md) restore much detail. They should not be copied uncritically: `durationMs: number` still admits negative durations despite a comment claiming a negative range cannot be written; mutable nonempty tuples can lose elements at runtime; a user-written predicate can make an unchecked claim. Python `NewType` and annotations likewise do not perform runtime validation. Type precision must earn its cost at an actual misuse or partial operation, and derive from a schema only where that schema truly owns the contract. No host integration is required beyond available checkers and runtimes.

**Simulated practitioner:** “OrderId should not silently fit where UserId is expected.” **Strong skeptic:** “Brands on every primitive and a blanket cast ban create ceremony while the real runtime boundary remains unchecked.” **Falsifiable evaluation:** supply swapped identifiers, an invalid JSON payload, an empty-list partial operation, and a harmless list sum. Pass if the first three gain appropriate protection while the sum keeps a plain list; fail if types alone are claimed to validate JSON or every value is branded.

**History and disposition:** [#174](https://github.com/cursor/plugins/commit/91be0f994b5de7a75f4d6f2b3b00958126d9195e) adds constructive modeling and “strengthen only where partiality appears.” [#634](https://github.com/cursor/plugins/commit/99743e9c151c8537cbbf1f98bb38f34ef3368453) removes those examples plus cast, exhaustiveness, and precision-limit guidance, claiming agents do as well without them. The remaining description still mentions exhaustiveness. No visible runs establish portability of that cut. **Adapt into shape/develop references**, retaining the precision-limit safeguard and correcting example guarantees.

## What to carry into the eight owners

This is a proposed editorial destination, not an automatic change list. A concrete observed failure should justify each later instruction edit.

| Owner | Distinct material worth considering | Boundary to preserve |
| --- | --- | --- |
| shape | Domain/invariant modeling; domain-facing boundaries; state ownership; conditional alternative prototypes; consumer workflow target | Do not redesign every new requirement or install speculative foundations. |
| develop | Boundary parsing; proportionate types; retry/crash semantics; coherent checkpoints; two-edit test reasoning | Existing repository tooling and actual language guarantees govern implementation. |
| debug | Reproduce and inspect state; legitimate-state distinction; interrupt repeated failed premises; measure actual work | A mitigation can be valid; broader fixes remain bounded by cause and scope. |
| review | Observable-contract tests; interface compression; actual artifact evidence; honest numerical claims | Report concrete defects rather than enforcing named-principle aesthetics. |
| research | Pre-run decision criteria; noise/confounder checks; source/evidence pointers; bounded extraction | Descriptive or single-run evidence can be useful when labeled honestly. |
| simplify | Reader indirection plus state burden; one owner for repeated decisions; scoped subtraction; consumer-complete API migrations | Do not equate fewer lines, fewer callers, or deletion with lower complexity automatically. |
| handoff | Actual verification and its limits; rerunnable evidence where useful; consumer-facing impact; preserved task state | No mandatory TSV, transcript capture, model-family review, or sibling dependency. |
| simulate-discussion | Identify contested premises and comparison criteria; distinguish simulated arguments from evidence | A plausible debate does not establish behavior, user preference, or measured benefit. |

The most valuable transfer is the reasoning in **test-behavior-not-implementation**, **attack-the-premise**, **make-operations-idempotent**, **separate-before-serializing-shared-state**, **model-the-domain**, **minimize-reader-load**, and **explain-the-number**. The largest adoption risks are absolute internal trust, mandatory tooling for every nontrivial task, universal redesign, unconditional subtraction, model-specific prompt cuts, and autonomy phrased without scope. These judgments are based on source inspection and falsifiable proposals above; they remain provisional until exercised on the user's actual daily work.
