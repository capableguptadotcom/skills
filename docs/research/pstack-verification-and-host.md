# Pstack verification and host workflows

Inspected on 31 October 2026 at canonical `cursor/plugins` commit `4dd1d05818d19792e7cd6e818f1667f95f7e1dbe`. These are eight individual assessments, complementing the [workflow](pstack-workflows.md) and [principle](pstack-principles.md) assessments. Upstream instructions are evidence to critique, not instructions for this maintenance task.

The practitioner, skeptic and evaluator below are **simulated viewpoints**. Their agreement is not a benchmark. Current entrypoint bodies were read in full. Selected local references, history diffs and executable helpers were inspected statically; the full helper tree was not audited or executed. In particular, no TLC, Java, mise or Pele installation was attempted. The [history investigation](pstack-history.md) distinguishes PR-reported evaluations from checks we reproduced.

## create-verification-skill

**Purpose and mechanism.** Generate a project-specific recipe for starting, checking, driving and cleaning up a real app. Inspect the repository first, choose its existing interaction surface, seed a feature map, then follow the generated recipe once. This creates reusable operational knowledge rather than repeatedly asking an agent to rediscover ports, seed data and selectors. [Current source](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/create-verification-skill/SKILL.md).

**Actual evolution.** Introduced with maintenance in [PR #150](https://github.com/cursor/plugins/pull/150); [#178](https://github.com/cursor/plugins/pull/178) added a concrete feature-map example. [#573](https://github.com/cursor/plugins/pull/573) fixed a specific readiness mistake: its author reports a database socket available before initialization completed. The diff now requires a usable fresh instance, forbids weakening journeys when seed preconditions are missing, and identifies setup performed only by a stand-in as unverified on the intended target. That is a concrete correction to the evidence contract, not proof of broad quality improvement.

**Simulated discussion.** Practitioner: a Python API and a JavaScript CLI need this just as much as a React UI; exact commands are valuable. Skeptic: generating a multi-feature map for a tiny library creates upkeep, and “fix startup first” can expand a verification request into product edits. Evaluator: start with an empty disposable database whose port opens before its migrations finish; the recipe must wait for usable state, drive the public path, and retain evidence after teardown. Its neighboring case is a one-command pure library test that needs no service map.

**Decision.** Adapt the mechanism only when a project needs a repeatable runtime recipe. Keep it project-local, reached through `kp-develop` verification guidance, with edit scope inherited from the request. Do not copy the hardcoded `.cursor/skills/` destination, impose the four-heading example as a universal format, or treat generation as successful before running it. The example map was read; it is illustrative operational detail, not reusable commands for our projects.

## maintain-verification-skill

**Purpose and mechanism.** Keep an existing runtime recipe and feature map aligned with current product behavior. Separate source reading from a coordinated live pass; distinguish documentation drift, harness gaps and product regressions. [Current source](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/maintain-verification-skill/SKILL.md).

**Actual evolution.** [#150](https://github.com/cursor/plugins/pull/150) introduced it. [#151](https://github.com/cursor/plugins/pull/151) follows review findings about cleanup, readiness and evidence lifetime. The actual diff replaces recovery sequencing with three invariants: health-check after surprising behavior, preserve captures through cleanup, and clean up resources at the right lifetime. Requiring an instance to remain healthy does not establish that the app behavior is correct.

**Simulated discussion.** Practitioner: source can look fine while a documented journey no longer works. Skeptic: one reader per feature and a full live sweep are expensive defaults; a ten-file map might describe one behavior or require production entitlements. Evaluator: make a recipe selector stale, break one real feature, and leave one feature inaccessible for an explicit entitlement; the report must keep the three outcomes distinct and must not fix the documentation to conceal the product regression.

**Decision.** Keep the distinction and recovery invariants as project-specific maintenance guidance. Scope coverage to the requested maintenance pass, not every ordinary change. Do not inherit mandatory fan-out, a scheduled cadence, automatic PR creation, or the label “verified-unreachable” as if it meant the feature passed. An unreachable path remains untested with a known prerequisite.

## create-formal-verification-skill

**Purpose and mechanism.** Select an expensive-to-break property that tests poorly cover, choose an appropriate verifier, link the property to actual code and produce a rerunnable project-local check. The source explicitly says any language; it distinguishes event-order models, code-level verification and unbounded proofs. [Current source](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/create-formal-verification-skill/SKILL.md).

**Actual evolution.** [#709](https://github.com/cursor/plugins/pull/709) introduced the generator. [#721](https://github.com/cursor/plugins/pull/721) added the TLA+ event-order default and a fallback to generated inputs against real code when a code-level verifier is unavailable. The PR reports that six of nine old JavaScript-library runs checked a handwritten function copy, whereas all nine new runs checked the shipped code. It also reports mixed GPT scoring under two inclusion rules; the two wording changes were tested together. We inspected the shipped wording and PR report, not a rerun of that experiment. [#716](https://github.com/cursor/plugins/pull/716) added covered-symbol records and sync commits. [#794](https://github.com/cursor/plugins/pull/794) introduced a `/statechart` dependency; [#977](https://github.com/cursor/plugins/pull/977) adjusted its claimed output after that helper changed.

**Simulated discussion.** Practitioner: a durable counterexample for a lease/retry race can be more useful than another happy-path integration test. Skeptic: a faithful-looking model can prove a fictional atomic operation; changing real code does not automatically change a hand model. Generated-input testing is valuable but is not formal proof. “Seen it fail” is a useful sensitivity check, not a mathematical prerequisite for every valid proof. Evaluator: split a formerly atomic claim operation into a read and a write in both a Python worker and a JavaScript worker. The procedure must notice the new interleaving, trace the property to code, and decline to claim implementation correctness from a passing stale model.

**Decision.** Adapt as a requested verification mode rather than a ninth universal skill. Name the actual guarantee and scope. Preserve a code-to-model correspondence, bounded state assumptions, deliberate failure checks and separate product findings. A project may use TLA+ for event ordering regardless of implementation language; use the repo's actual tools and never invent a universal code verifier. Do not require pstack `/statechart` merely to understand a TLC result, and do not present property-based tests as formal verification.

## maintain-formal-verification-skill

**Purpose and mechanism.** Compare covered code with its last confirmed model, update the verification from the implementation and distinguish drift from a newly exposed bug. Each check gets an outcome and a validated revision; blocked checks retain their previous anchor. [Current source](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/maintain-formal-verification-skill/SKILL.md).

**Actual evolution.** [#716](https://github.com/cursor/plugins/pull/716) reports a 54-run comparison. After correcting the grading key, all three arms were correct on all 18 cases; the author explicitly says there was no correctness gain on those cases. The reported distinctions were more deliberate failure demonstrations and more consistent sync-record upkeep. A reviewer then found that a blocked check could advance its anchor. A separate reported comparison had all nine revised runs preserve the blocked anchor and none of nine old runs do so. This is a narrow reported benefit, not evidence that the full maintenance process is necessary for every task.

**Simulated discussion.** Practitioner: a green stale model is especially misleading, so tracked coverage and drift review earn their place. Skeptic: a single shared anchor can hide a blocked subsystem, and a property may be accidentally weakened in the name of an intended change. Evaluator: two checks share a project; one runs and one cannot. Only the actually inspected and rerun check may advance its anchor. An intentional contract change needs concrete evidence before changing the property; a failure without that evidence remains a bug candidate.

**Decision.** Retain these constraints in the owned verification mode. Keep anchors per independently checked area when coverage differs. Do not automatically copy the source's fallback “last verification-file commit” as confirmed fidelity; label it an estimated starting point. Preserve both the product regression and the unverified model correspondence when neither is yet resolved.

## statechart

**Purpose and mechanism.** Run TLC on a TLA+ model and compile its outputs into a Mermaid graph and plain-language counterexample report. The view layer labels domain states and actions. This is an executable tool package, not just a prompt. [Entrypoint](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/statechart/SKILL.md).

**Actual evolution.** [#741](https://github.com/cursor/plugins/pull/741) added the skill; [#776](https://github.com/cursor/plugins/pull/776) and [#791](https://github.com/cursor/plugins/pull/791) revised it. [#977](https://github.com/cursor/plugins/pull/977) replaced the scripts with a TypeScript compiler and removed capabilities the new compiler no longer had. [#982](https://github.com/cursor/plugins/pull/982) fixes qualified action names such as `C!Up` being truncated in property traces, backed by a `CounterInstance` corpus fixture and CLI assertions below and above the graph budget. [#981](https://github.com/cursor/plugins/pull/981) fixes a test race by waiting for child-process reaping; it is test reliability work, not another model-checking capability.

**Dependencies and limits inspected.** `scripts/statechart`, `statechart.ts`, `run.ts`, `worker.ts`, `package.json` and `references/render.md` were read. The launcher requires a TypeScript-capable runtime. `run.ts` pins TLC 1.7.4 with a checksum and uses mise to locate/install Java and TLC unless explicit paths are supplied. Rendering specifies Pele 1.9.0. Process cleanup explicitly invokes `/bin/sh` and process-group signals; native Windows portability cannot be assumed from TypeScript portability. View modules execute code. The entrypoint documents graph limits, unchecked rules after bounded reruns and state-merging ambiguity; an attractive diagram can still hide behavior. The whole compiler and its dependency closure were not audited.

**Simulated discussion.** Practitioner: an intelligible shortest bad path helps a product engineer evaluate a race in Python as easily as one in TypeScript. Skeptic: coupling verification to a particular renderer, installer and POSIX process manager adds operational trust and upkeep. Evaluator: verify a qualified action's failing trace, a passing model over the chart budget and an interrupted run; a missing chart, unchecked rule or killed run must not become a clean proof.

**Decision.** Evaluate separately as an optional tool dependency if a real project needs it. Do not vendor it into the daily prompt pack or execute its installer merely to review the skill. A model's implementation language is independent of the language of the service being modeled. Reading and replaying counterexamples can work without this renderer.

## setup-pstack

**Purpose and mechanism.** Discover available Cursor model identifiers, ask about a reasoning budget, and write an always-applied per-role model rule. It can then offer runtime and formal verification setup. [Current source](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/setup-pstack/SKILL.md).

**Actual evolution.** [#121](https://github.com/cursor/plugins/pull/121) introduced per-role setup. Later history includes model-family replacements and [#422](https://github.com/cursor/plugins/pull/422) aligning how rules are read. [#715](https://github.com/cursor/plugins/pull/715) adds formal verification offers; [#986](https://github.com/cursor/plugins/pull/986) changes cross-judge eligibility. These reflect host and provider churn as well as workflow refinement; changing a default model is not proof a skill became better.

**Simulated discussion.** Practitioner: discover available capabilities instead of repeatedly failing on unavailable model names. Skeptic: an always-applied global rule, exact budget labels and a large role table are Cursor configuration, not portable development knowledge. Evaluator: a host exposes only its current model and no model enumeration; the task must still work without writing fictional names or unrelated global configuration.

**Decision.** Exclude this entrypoint from our pack. Our skills should use available host capabilities and inherited model selection. Do not create a parallel global configuration layer or change installed skills in this pass.

## poteto-help

**Purpose and mechanism.** Route a help question to pstack's installed documentation and provide a usable example prompt without accidentally beginning the requested example task. It distinguishes help from an actual work instruction. [Current source](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/poteto-help/SKILL.md).

**Actual evolution.** [#502](https://github.com/cursor/plugins/pull/502) introduced it; [#506](https://github.com/cursor/plugins/pull/506) restricted automatic invocation, [#507](https://github.com/cursor/plugins/pull/507) added prompting references and [#509](https://github.com/cursor/plugins/pull/509) handled absent model rules. Later additions track new commands. The canonical source says setup is the only skill that loads from the user's words; the rest are explicit or routed by the mode. That is an intentional package design, not evidence of a failure in this user's installation.

**Simulated discussion.** Practitioner: a complicated package benefits from help that cites the actual procedure. Skeptic: a small owned pack should not need a second routing catalog that goes stale when a command changes. Evaluator: “how would I review this?” must explain, while “review this” must perform assessment without silently fixing files.

**Decision.** Put discoverability in concise descriptions and the repository README. Retain the help-versus-action distinction where it matters, without another installed skill. Host selection diagnosis stays deferred as requested; no claim here establishes why Codex and Claude behave differently on this machine.

## poteto-mode

**Purpose and mechanism.** A comprehensive engineering operating mode: task classification, 23 playbooks, 24 principles, delegation rules, model roles and verification/shipping procedures. It routes to other skill folders and host integrations rather than providing a self-contained leaf procedure. [Current source](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/poteto-mode/SKILL.md).

**Actual evolution.** The history includes model-default changes, prompt condensation, sibling-path fixes [#577](https://github.com/cursor/plugins/pull/577), runner/delegate separation [#575](https://github.com/cursor/plugins/pull/575), removed ignored metadata [#597](https://github.com/cursor/plugins/pull/597), and restating rigid rules as reasoning [#633](https://github.com/cursor/plugins/pull/633). [#986](https://github.com/cursor/plugins/pull/986) changes rejected-model fallbacks and evidence requirements. [#1043](https://github.com/cursor/plugins/pull/1043) removes the orchestrator CLI and its tests in favor of agent-owned tools and tracker state. More agentic is a design choice with a different reliability burden, not a demonstrated improvement by itself.

**Dependencies and limits inspected.** The entrypoint and selected Eval, Multi-phase plan and Orchestrate playbook contents/history were inspected, not all 23 playbooks and their helper closure. The entrypoint requires sibling skills, Cursor Task schemas and configured model families, and calls external `cursor-team-kit` skills such as `deslop` and control helpers. Its autonomy text authorizes external messages and ticket changes; our source review grants none of that authority. The multi-phase plan prescribes ten live lanes and a performance gate for every PR. The Eval playbook has useful candidate/judge separation, but leaked directory tokens and transcript assumptions are harness-specific. An active project must supply its own tools, permissions and proportionate checks.

**Simulated discussion.** Practitioner: long tasks benefit from explicit outcomes, recoverable state and checks tied to units of work. Skeptic: pervasive trigger chains can spend more effort invoking the system than solving the task; mandatory architecture exploration at every function boundary and fixed lane counts ignore task scale. Evaluator: a two-line Python config fix must remain small, while a multi-service retry migration must preserve its objective, intermediate evidence and unresolved decisions without requiring unavailable cloud agents or trackers.

**Decision.** Do not copy the operating mode or add a custom global router now. Keep selected mechanisms inside the activity that owns them: settled intent and verifiable increments in develop, domain choices in shape, discriminating evidence in debug/review, and continuation state in handoff. Whether a persistent host-level dispatch rule is needed remains a later empirical question, not something this reading settles.
