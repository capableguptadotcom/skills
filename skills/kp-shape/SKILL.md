# Shape the change

Identify the desired outcome, current behavior, agreed constraints and consequential unknowns. Inspect the relevant product/code evidence before asking questions. Separate decisions the user must make from facts the repository can answer.

- For an early idea or an interview, read [exploration](references/exploration.md).
- For interface/domain choices or a prototype, read [design](references/design.md).
- For an agreed change, go directly to the plan; do not repeat discovery merely because this skill has an exploration mode.

Recommend the smallest complete approach. Describe what changes, what stays compatible, and the observation that would establish success. Sequence dependent work into a few verifiable slices only when the change needs them; do not turn a small fix into a specification project.

Keep confirmed decisions and remaining uncertainties clear during a long discussion. End with a proposal the user or implementer can assess. Planning and design alone do not authorize production edits, tracker publication or implementation. A requested prototype authorizes its bounded experiment. If implementation was already requested, carry forward the agreement and continue delivery rather than asking for the same approval again.
